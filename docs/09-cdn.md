# 9. CDN套用

给"哪天 VPS 的 IP 被墙"备一条后路：菜单 9 每条起一个独立的 `xy-cdn-<n>` 实例、跑一个
**VLESS + WebSocket + TLS**（或所选协议）节点，套 Cloudflare 橙云中转——客户端连的是 **CF 的 IP**、
不是你 VPS 的真 IP，所以真 IP 被封了这条仍能用。与主节点完全隔离（独立服务/配置/证书），重装
主节点不受影响，也能单独卸载。

> 进菜单顶部就是简短说明。**执行前**：① 域名解析绑到本机 IP、开【橙色云】代理（必须橙云）；
> ② VPS 放行端口 2053/2083/2087/2096/8443（商用 VPS 一般全开放）；③ CF 的 SSL/TLS 模式选【Full 完全】。

- **可加多条**：`1 CDN节点安装` 里**协议可多选**（逗号分隔如 `1,3,4`、或 `a` 全选），一次把选中的都装上
  （共用你输入的那个域名、各占一个端口/服务）。已装过再进 `1` 会问 **y 清空重装 / a 追加新增 / 回车返回**。
  `3 查看` 上方列已配置节点（含各自的优选地址）、下方列全部备用链接；`5 卸载` 可选删某条、**多条（逗号分隔如 1,3）**或全部；`2 优选地址`（测速筛候选 / 手动填）见下。
  装完会**直接问要不要筛一批优选候选**（回车即筛），以后想换进 `2` 就行。
  CF 免费版可代理端口有限，最多 5 条。
- **不需要 Let's Encrypt**：CF 的 SSL 模式用 **Full（完全）**，源站自签证书即可（CF 不校验源站
  证书，客户端看到的是 CF 的有效证书）——省了 80 端口验证、证书续期一堆麻烦。
- **不需要 Origin Rule**：默认走 CF 可代理端口（2053/2083/2087/2096/8443，两端同口），避开主节点的 443/8443。
- 新增时可选**协议**（`1 VLESS+WS`·最稳 / `2 VLESS+XHTTP`·最快 / `3 VMess+WS` / `4 Trojan+WS`）、
  **核心**（sing-box / xray，XHTTP 入站仅 xray 支持会自动用 xray）、**名称前缀**（默认沿用安装前缀，
  如 🇯🇵；没设过可自定义；回车则 `CDN·协议`）。
- **写入订阅按客户端支持度自动筛选**：VLESS+WS / VMess+WS / Trojan+WS 三格式全支持；VLESS+XHTTP
  只有 mihomo 认，写入时 sing-box / 小火箭订阅自动跳过。无论哪种，**单条备用链接始终照常给出**
  （客户端自己怎么用不受订阅筛选影响）。
- 子菜单 `4 全部节点写入/移出订阅`（循环开关）：把全部 CDN 节点一键**并进三条订阅**并自动刷新
  （客户端拉一次即见）；再按一次即移出。**没装主节点也能生成订阅**（此时订阅只含 CDN 节点，但
  订阅地址走本机 IP，本机 IP 被墙则订阅地址也拉不到——节点本身经 CF 仍可用，改用单链接导入）。
- 前提：**一个域名 + 挂到 Cloudflare（免费版即可）**。

## 优选地址（CDN 子菜单 2）

套 CF 之后客户端连的是"域名解析到的那个 CF 任播 IP"——运营商给你分到哪条线路就走哪条，
经常落到又慢又挤的边缘上。**优选**就是把分享链接里的**地址位**换成一个更快的 CF 地址，
而 **`sni` / `host` 仍是你自己的真域名**：CF 靠 Host 头回源，所以随便换哪个边缘都连回同一台 VPS，
**服务端配置、证书、CF 后台一律不用动**。

> ⚠️ **一句话前提**：本机测速测的是「**VPS → CF 边缘**」，而决定你体感的是「**你的网络 → CF 边缘**」。
> 这两段常常一致（同一批边缘、同一个大区），但**不保证**。所以本机测速只当**粗筛**用，
> 最终该选哪个，只有客户端说了算——下面 `2` 的设计就是围着这一点来的。

- **`1 测速筛候选`**（推荐；**装 CDN 节点时会直接问一次，回车即筛**）：本机粗筛出若干个
  还不错的 CF 边缘，**每个生成一条节点写进订阅**（`CDN·优选1` … `优选N`），
  **最终由客户端的 URLTest 挑最快的那条**。
  - 粗筛流程：拉 **Cloudflare 官方 IP 段**（`cloudflare.com/ips-v4`，拉不到用内置兜底段）
    → 切成 `/24` 打散随机采样（默认 500 个）→ **多线程 TCP 握手筛延迟**
    → 延迟最优的前几名跑 **`speed.cloudflare.com` 下载测速** → 取吞吐最高的前 N 个当候选。
  - 候选节点**共用同一个服务端入站**（uuid/path/端口全一样），**不新建任何服务**，
    区别只在客户端连哪个 CF 边缘。协议自动挑兼容性最好的那条（vless-ws 优先）。
  - 测速端口默认沿用你 CDN 节点的 CF 端口（顺带验证该边缘对这个端口确实放行），
    全挂时自动用 443 复测一轮。

- **`2 手动填`**：填第三方公开的优选域名，或某个具体 CF IP，写进**全部 CDN 节点**。
  写入前先从本机 TCP 握手探一下，不通会警告让你确认（本机不通 ≠ 客户端不通，最终由你拍板）。
  **留空回车 = 取消优选**、恢复用域名。已经在客户端侧跑过优选工具、心里有数的，用这个最直接。

- **`3 清空候选`**：把候选节点从订阅里撤掉（基础节点和手动优选地址不动）。
- **`4 测速参数`**：候选数 / 名次 / **写进订阅的候选数** / 并发 / 超时 / 单个下载量 / 时长 /
  候选下限 / 测试端口，都能调，范围有校验。

> ⚠️ **下载测速是真的在下数据、走你 VPS 的流量**：一轮最多 `名次 × 单个下载量`，默认 6×10 = **60MB**，
> 每次执行前都会先告诉你本轮上限并让你确认。流量包紧的把名次和下载量调小，或者干脆只用 `2 手动填`。

### 为什么是「多候选」而不是「定时自动优选」

早期版本做过定时自动优选（cron 到点重测、自动换地址），**已经移除**——它在真实链路上交付不了：

```
VPS 换了地址 → 多机聚合时主机得有人点『更新配置』 → 客户端还得重拉订阅
                        ↑ 人工断点                        ↑ 人工断点
```

换一次地址中间隔着一到两个人工步骤，定时只会造成"它在自动工作"的假象——你以为在优选，
客户端其实几天都还用着老地址。

多候选没有这个问题：**写进订阅的内容是稳定的**，不需要频繁刷新；客户端的 URLTest 按自己的
`interval` 一直重测，从候选里挑当下最快的。而且它测的正是那段唯一重要的路径。
候选池隔一段时间手动重跑一次 `1` 就够了。

实测（东京 VPS，国内移动网络）能说明为什么必须让客户端来选：

| 候选 | 本机(VPS)测速排名 | 客户端实测延迟 |
|---|---|---|
| 优选1 | 第 1（939 Mbps） | 351 ms |
| 优选2 | 第 2 | 280 ms |
| **优选3** | 第 3 | **103 ms** |
| 优选4 | 第 4 | 369 ms |
| 优选5 | 第 5 | 483 ms |

本机排第一的那个，在客户端只有 351ms；真正最快的是本机排第三的。
未优选时同一批 CDN 节点是 461~522ms——**优选后 103ms，和直连节点同一档**。

顺带一提：CDN 节点的名称带国旗前缀，会被作者模板里 `🇯🇵日本随机` / `♻️全部随机` 这类
`url-test` 分组自动收进去（`include-all: true`），所以候选写进订阅后**不需要任何客户端配置**。
平时直连节点更快，候选沉在底下不碍事；哪天直连 IP 被墙，URLTest 自动从活着的候选里挑最快的顶上
——这正是 CDN 套用该有的行为。

> 另外：**优选地址不会被写进「节点服务器直连」规则**。那些规则是给"你访问自己的服务器"用的
> （SSH/管理流量不走代理），而优选地址是 **CF 的共享任播边缘**，上面跑着海量第三方站点，
> 写成 DIRECT 既误伤别人又毫无用处。这类节点的直连目标认的是 Host 头里你的真域名。
