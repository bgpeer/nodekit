# 16. 自建Emby

在这台机器上再跑一套 **Emby + OpenList + AutoFilm + MediaWarp**。网盘（夸克、阿里、115 等）
挂进 OpenList，AutoFilm 定时把里面的影片生成 `.strm` 文本挂进 Emby 媒体库，播放时 MediaWarp
拦截请求并 **302 重定向到网盘直链** —— 视频流直接从播放器到网盘，**不经过你的 VPS 带宽**。
本地只落地几 KB 的 strm，小盘机也能开大媒体库。

装完敲 **`emby`** 甩出面板地址，敲 **`media-stack`** 看全部地址和密码，
`media-stack 302` 可验证直链是否真的生效。

## 和节点的关系：不会把节点搞坏

`media-stack.py` 是独立文件，只**读**节点的域名（`state.json`）、nginx 内部 https 端口和
acme 证书状态；只**写**它自己的 `/etc/nginx/conf.d/media-stack.conf` 和安装目录，
**绝不碰** `nginx.conf` / `bgpeer.conf` / `bgpeer-stream.conf`。写 nginx 前先 `nginx -t`，
不过就自动还原备份。

节点开了 SNI 分流也没关系：分流表的 `default` 已经兜到内部 8443，媒体子域名自动落进去，
**不需要改节点的任何配置**。

**端口**：不占 80/443。Emby 的 8096 会被收进 `127.0.0.1`（直连它会绕过 302 拦截，
退化成服务器中转），对外只走 MediaWarp。

## `3 挂载路径`

一个网盘一屏，各管各的。外面一行一个盘，右边是它现在扫什么。点进一个盘，编号跟着这张表往下排（没有的项不占号）：

| 项 | 哪些盘有 | 做什么 |
|---|---|---|
| `网盘扫码登录` | 115、夸克 TV、阿里（挂好的） | 里面有扫码登录和 `退出登录`（退出前会醒目地说后果、默认否）；当前一栏写已登录 / 掉线了 / 未登录（阿里还写是哪条接口）。换号直接扫另一个号；同一个号再扫只是刷新登录 |
| `扫码挂上` / `＋ 添加阿里云盘` / `＋ 添加 WebDAV` | 没挂的 115、夸克 TV、阿里；WebDAV 常驻 | 在这台机器上挂盘，不用去 OpenList 网页 |
| `修改扫描路径` | 每个盘 | 见下面「扫描路径」 |
| `生成媒体库` | 每个盘 | 只扫这个盘；当前一栏写它的定时 |
| `直链方式` | 每个盘 | 见下面「直链方式」 |
| `片名用哪个` | 每个盘 | 刮削结果 / 网盘文件名 |
| `不扫的目录` | 每个盘 | 见下面 |
| `名称重定义` | 每个盘 | 见下面 |
| `转码挑档` | 夸克 TV | 开关 + 它要用的本机那份夸克登录（打开时没登录会当场让你扫） |
| `只拿令牌（自己去 OpenList 填）` | 没挂的 115 | 只扫码拿令牌，不挂盘 |
| `截封面` | 挂好的盘 | 这个盘里没图的**全部截一次**（确认后放到后台截，不用等；截着时再点进去只看进度、可以停，不会再起一轮），不受每小时 / 每天的张数和流量限制 ⚠ 会消耗 VPS 流量（每张的保险照留：不认跳转的源不拉，一张超过 40 MB 当场掐断） |
| `补时长` | 挂好的盘 | 这个盘**单独关掉**自动补时长。只能单独关、不能单独开 —— 总开关（`7 设置 → 10`）关着时所有盘都不补，流量上限也只有总开关那一个 |
| `刷新元数据` | 挂好的盘 | `1 手动刷新`：这个盘里缺简介或缺图的电影 / 剧集 / 整部剧叫 Emby 去 TMDb 补一次，齐全的不碰；`2 自动刷新`：**默认关**，回车 = 每天北京时间 03:30，`0` = 关 |

扫码的盘（夸克 TV、115、阿里）二维码直接画在终端里，**一次画两个**：上面是网盘给的原码，下面是拉方的小码，哪个扫得上用哪个；
量得出终端字格、或你挑过一次（输 `w` 回车换宽度）之后只画那一个。115 的图片链接、夸克码里的链接照样给，终端扫不了就用链接。
菜单里回车 = 返回。

**不用去 OpenList 网页也能挂盘**：没挂的 **115 网盘**、**Quark TV**、**阿里云盘**、**WebDAV** 一直列在这一屏，
点进去 `1 扫码挂上` —— 先问挂到哪个路径（回车用默认 `/115`、`/quark`），再扫码。
夸克 TV 的二维码直接画在终端里，截图后夸克 App 从相册扫也行；挂上默认转码流。
WebDAV 那一屏的 `1 ＋ 添加 WebDAV`（挂几个都行，每个 WebDAV 那一屏都有）依次问地址、用户名、密码（不回显）、挂到哪；WebDAV 只能走本机代理，
⚠ 视频走 VPS 流量。挂不上会把刚建的存储撤掉。阿里云盘点 `1 ＋ 添加阿里云盘`：
默认在终端里直接扫 TV 版二维码，也可以去取令牌的网站扫完把刷新令牌贴回来。
115 的直链按换链时的 UA 签发，Emby 里播 115 由本机的小服务拿**播放器自己的 UA** 换链再 302
（MediaWarp 自己换的链只认它自己），视频照旧手机直连 115、不走 VPS 流量。

* **扫描路径** —— `1 添加` / `2 删除` / `0 返回`。**一个盘想挂几条挂几条**，加进去是追加。
  挑路径是**一层一层往下走**的，不用手打：编号＝进这一层，多个编号（逗号隔开）＝
  一次选好几个，`.`＝就选这一层，`*`＝这一层全部，`..`＝上一层，
  也可以**直接把路径贴进来**。所以 `/网盘/mov/电影/` 底下按 A、B、C… 分类的盘，
  钻到那一层按 `*` 就全挂上了。删也支持逗号隔开多条和 `*` 全删。
  **有最大的就扫最大的**：`/网盘` 和 `/网盘/mov/电影` 同时写进去，只留 `/网盘` ——
  扫整个盘本来就包含那条子路径，留着两条只会让人以为"限定了只扫电影"。
  ⚠️ 别选「整个盘」：手机备份、截图、扫描件都会变成媒体库里的条目，
  Emby 拿这些去刮削当然搜不到，表现就是「一堆条目全都没有海报」；
  而且扫描阶段会把网盘里的图片一张张拉到本地占硬盘。填到影视目录那一层。
* **不扫的目录** —— 扫描路径的反面：这个盘里**哪几棵子树不要进媒体库**。
  `1 添加`（和扫描路径一样点编号挑，不用手打）/ `2 删除` / `0 返回`。
  这一屏还会**自己点名**：本地 strm 树里还挂着 `BDMV` 的那些原盘，就是 Emby 里
  `0B / 0bps` 点开 `load fail` 的条目（用户看到的「一个显示 7.8 Mbps、一个没有」，
  没有的那个就是它）。它们归 `3 原盘怎么办` 管，**默认不进库**，不用写规则。
  典型场景是**同一部片网盘里存了两份**：一个合集里既有 x265 压制版又有 BDMV 原盘，
  Emby 里就是两个同名同海报的条目，其中原盘那个是 `0B / 0bps`、点开 `load fail`，
  用户点中坏的那个的概率是一半。给原盘那个目录加一条规则，一次清干净。
  规则按**整段**匹配（`合集` 不会误伤 `合集电影`），也可以写多段
  （`电影/合集/原盘`）。加规则时会先把「命中几个目录、几个 strm、
  这个盘一共多少」摆出来再问。
  ⚠️ 删的只是**本机生成的 strm**，网盘里的片子一个字节都不动 ——
  规则删掉再扫一次就全回来。AutoFilm 拦不住，所以每次生成之后、每天对齐之中各清一遍。
  > **为什么不用 Emby 的「多版本合并」去重**：那个开关脚本是故意关掉的。它按
  > 「清理后的文件名 + 刮削到的元数据」分组，网盘里名字相近的两部片会被强行并成一个条目；
  > 而且合并后的条目挂着两个源，探测失败的那个时长是 0，Emby 拿它算续播百分比就判定
  > 「看完了」，续播点存不下来。拿一个已知会坏进度条的开关去解决重复，是拆东墙补西墙。
  >
  > **为什么不自动认哪份多余**：「原盘旁边有同名压制版就删原盘」要赌片名清理对了、
  > 两份确实是同一部、用户想留的是压制版那份 —— 赌错一次就是删掉唯一的一份。
* **直链方式** —— 进去列的是**这个盘真的有的开关**，一项一行，各改各的。
  ⭐ **第一次见到一个盘时，脚本会按驱动把它调到实测能播的那一档**（在「4 生成媒体库」
  那一步做）——装完就能播，不用自己一项一项试：

  | 驱动 | 默认设成 | 为什么 |
  |---|---|---|
    | WebDAV / FTP / SFTP / SMB / local / crypt | **本机代理 + 伪装成浏览器** | 这三类在网盘侧**压根没有 CDN 直链**，本机代理是它们唯一的路；而字节一旦经过本机，Emby 的探测（ffmpeg 的 UA）就会被上游按 UA 挡掉，条目永远探不到音视频轨、点开 `load fail` |
  | 夸克 TV | **转码流** | 跨境线路上原画拉不动；转码流靠分片重定向在 Emby 里能播，实测 10.9 MB/s 对原画 306 KB/s。**只对新挂的盘**，已有的夸克不动 |

  > **转码流开头不再一卡一卡**：夸克转码流的播放列表里分片是相对路径，播放器原来每一段都先回
  > 你的 VPS 再跳去夸克（开头一两百 KB/s、三四十秒才上来）。现在开播那一下由本机把播放列表取来、
  > 分片补成完整地址再交给播放器，之后每段手机直连夸克（实测开播 4.6~4.9 MB/s，视频照旧不过 VPS）。
  > 默认开；某个源不认就 `media-stack hls-direct off`。阿里转码流不走这条（它的分片签名十几分钟就过期）。
  | 阿里云盘 | 不动 | OpenList 的默认（原画直链 · 开放平台接口）就是对的 |

  ⚠️ **只在第一次见到那个盘的时候设一次**，之后你改成什么都不会被改回去——替你做一次
  选择是帮忙，反复把你的选择改回来是耍流氓。
  判断标准只有一条：**这个字段已经在它的存储配置里**。OpenList 每个驱动的字段各不
  相同（同一件事夸克叫 `link_method`、百度叫 `download_api`），而写一个驱动没有的键
  进去，OpenList 会原样存着然后完全忽略 —— 屏上凭空多一个看着能用的开关、切完什么都
  没变，比没有这个开关更坏。所以宁可少给，绝不给假的。目前收录：
  * **画质** —— 夸克 / UC 的 TV 版驱动（`link_method`）、PikPak（`use_transcoding_address`）：
    `原画直链` ↔ `转码流`。
    ⚠️ **转码流在 Emby 里播不了，只对 OpenList 网页播放器有用。** 转码流给出的是
    `m3u8`，而 `m3u8` 里的分片写的是**相对路径**；Emby 是 302 过去的，播放器会把相对
    路径拼到自己以为的基址（`/emby/Videos/<条目id>/`）上，于是分片请求全打回 Emby，
    一路 `401`，客户端表现就是**一直转圈**（日志里每秒好几条 401）。网页播放器没这个
    问题——它的基址本来就是网盘。
  * **取直链的接口** —— 百度网盘 / Terabox 这类有 `download_api` 的：官方 ↔ 非官方。
  * **接口通道** —— 阿里云盘：`default` 走第三方开放平台接口，阿里对它限速
    （实测约 0.8 Mbps）；`alipanTV` 走 TV 客户端通道。
    ⚠️ **类型和令牌必须一起换**：OpenList 按类型决定向官方 API 报哪个驱动标识，
    拿一种流程取的令牌去另一种那边换，就是 `empty token returned from official API`。
    所以菜单里换通道时会当场要你贴新令牌，去 <https://api.oplist.org/> 选对应那一项扫码。
  * **回源方式** —— **每个盘都有这一项**，跟驱动无关。它管的不是画质，是
    **视频的字节从哪儿走**：`302 直链`（默认，播放器直连网盘，不吃 VPS 带宽）↔
    `本机代理`（每个字节先过你的 VPS，吃双份带宽、也更慢）。
    留着代理这一档是因为：有的网盘发的直链绑 IP、绑 UA，播放器自己去连就是 403，
    这类盘**不代理根本播不了**；WebDAV 源和本地目录这两类驱动更是在网盘侧压根没有
    CDN 直链。跑 `tools/dav-check.sh` 能看到每个盘现在实际走的是哪条。
  ⚠️ **「没有画质开关」不等于「没有直链」**：115、WebDAV 这些盘照样 302，
  只是没有「原画/转码流」这个**选择**。这类盘播放慢通常是网盘那边限速，
  `tools/ali-403.sh <片名>` 可以量出来。
* **片名用哪个** —— 按盘设，默认跟全局走。网盘文件名带 `[第154集•4K]` 这类标记的盘，
  Emby 解析不出片名、拿去刮削就是乱撞，选「网盘文件名」更准（只锁标题这一个字段，
  海报简介照常跟着刮削更新）；文件名规规矩矩的盘用「刮削结果」。
* **名称重定义** —— 默认**关**，和「片名用哪个」同一套三态（开 / 关 / 跟默认走），
  「♻ 剩余网盘」那一屏改的是默认值。开了之后，本机 strm 的**文件名**换成清洗过的
  「片名 (年份)」，网盘里的文件名一个字都不动。
  解决的是这一类：网盘文件名叫 `[[豆瓣6].1分]华丽上班族.Office.2015.BD720P.国粤双语.高清中字`，
  Emby 把**开头的方括号**当发布组标签整段剥掉，剩下 `.1分]华丽上班族.Office` 拿去 TMDb
  当然搜不到 —— 表现就是**一大批条目没有海报**，而文件本身好好的、点开就能播。
  实测一个 2757 部的库里有 797 部（29%）栽在这上面。

  | 网盘原名 | 清洗后 |
  |---|---|
  | `[[豆瓣6].1分]华丽上班族.Office.2015.BD720P.国粤双语.高清中字` | `华丽上班族 (2015)` |
  | `[妖怪都市 1992].DVDRip` | `妖怪都市 (1992)` |
  | `[某某电影 4K 国粤双语]` | `某某电影` |
  | `[菲利普船长].超清中英双字` | `菲利普船长` |
  | `Some.Movie.1998.BluRay.1080p.x265.10bit.2Audio-GROUP` | `Some Movie (1998)` |
  | `流浪地球 (2019)` · `老友记 S01E01` · `156 4K` | **不动** |

  中文片名后面跟着的英文别名会一起丢掉（`血仍未冷.The.Replacement.Killers.1998` →
  `血仍未冷 (1998)`）——刮削器拿中文名去搜更准，留成一串反而两边都对不上。
  清出来**只剩数字**的（`156 4K` → `156`）一律不动：那是集号，改名只会更糟。
  `1/2/3` 之外还有 `4 预览`（只列不改）和 `5 撞名的怎么办`。
  清出来的「片名」里还带着 `豆瓣`/`评分`/`imdb`/`4kyu`/`xxx.cc` 这类**站点标记**的，
  一律不动——那说明清到的是发布站的名字，改上去比不改更糟（Emby 拿它去搜永远搜不到，
  而原名说不定还能搜到）。
  ⚠️ 改名走的是和「扫描路径改了要挪 strm」同一条路（`migrate_strm_layout`），所以
  **nfo/字幕/海报跟着搬、续播点按网盘路径记下来再贴回去**——条目 id 会变，看到哪儿不会丢。
  AutoFilm 下一轮仍按网盘原名生成一份，它一进来就会被挪到同一个清洗后的名字上，
  不会变成一部片两个条目。
  ⚠️ **两个不同的文件清出同一个名字时**（`[片名].超清中英双字.mp4` 和 `[片名].1080p.mkv`
  都会清成「片名」），挪过去是**静默覆盖**，库里会少一部片还查不出来。默认
  **这几个一律不动**，警告里连 `原名 → 目标名` 一起打出来。
  想全都保住就把 `5 撞名的怎么办` 改成 **加后缀区分**：把原名里被清掉的标记接回片名
  后面——`菲利普船长 - 超清中英双字` 和 `菲利普船长 - 1080p 国粤双语`，两个名字都读得懂、
  都刮得到，一部都不少。标记也一模一样时再按原名排序补 `(2)` `(3)`。
* **♻ 剩余网盘（自动）** —— 只管**没有单独设过路径**的盘，永远排在它们后面。
  开着的话，新挂的网盘会自动按整个盘进 Emby；单独设过路径的盘不受它影响。
  那一屏：`1 自动路径开关`/ `2 生成媒体库` / `3 直链方式` / `4 片名用哪个` / `5 不扫的目录` /
  `6 名称重定义` / `7 组里单个盘的设置`（扫码登录、转码挑档这些各盘自己的都在这里）/ `8 截封面` / `9 补时长` /
  `10 刷新元数据`。5、7–10 先挑组里哪个盘，再进那个盘自己那一屏 —— 每个盘各管各的。
  它的「直链方式」是**先列出这批盘各自现在是什么**，再进某一个盘去改 ——
  这一批里可能混着夸克、阿里、115、WebDAV，各有各的开关，没有一个统一答案。

> **为什么「OpenList 网页里播很流畅、Emby 里卡」**：两边取的根本不是同一条流。
> OpenList 的在线播放器走的是网盘的**转码流**（阿里 `getVideoPreviewPlayInfo`、
> 夸克 `getTranscodingLink`），码率低一个量级、而且通常不吃下载限速；
> 而 302 给播放器的是驱动 `Link()` 返回的那条，也就是**原始文件**的下载地址。
>
> 夸克能把这两条对齐，是因为 `QuarkTV` 驱动在 `Link()` 里留了个岔路口：
> `link_method=streaming` 时直接返回转码流 —— 所以把它切成转码流，Emby 就和网页
> 一样流畅了。**`AliyundriveOpen` 没有这个岔路口**，`Link()` 写死走 `getDownloadUrl`；
> 转码流它也有（网页播放器用的就是），但没有任何开关能让 302 用上它。所以夸克那套
> 修法在阿里盘上照搬不了，只能换通道（`alipanTV`）、买权益包，或者把大码率的片子放夸克。

`8 更新` 会在换完镜像之后把**组件版本更新前后并排打出来**：

```
  组件版本
    Emby       4.8.11.0  →  4.9.0.42  有更新
    OpenList   v4.1.2   （没变）
    MediaWarp  2026-09-10 构建  →  2026-09-14 构建  有更新
```

这套东西全用 `:latest` 标签，拉完只说「镜像已更新」的话，**到底更到了哪一版一个字都没有** ——
出了问题想回溯「那天更了什么」除了猜没有别的办法。Emby 重启要十几秒，太早问只会拿到空串，
所以会等到问出版本号为止；实在问不到就写「这次没问到」，**不编**。更新前没问到的也只报
现在是什么，不说「没变」——那是不知道，不是没变。

### 小雅（自建 WebDAV）

「3 挂载路径」最后一栏「小雅（自建）」。不动现有架构：小雅单独一个容器，接在媒体栈内部网络上、不对外开端口，
docker-compose 不改、别的容器不重启；OpenList 里多挂一个 `/xiaoya`（WebDAV，跟七米蓝一样走本机流量）。

1. **阿里令牌**：填小雅要的三样（阿里云盘 token、open token、转存文件夹 ID），不回显，存在 `/etc/xiaoya`（只有 root 能读）。
   要**另取一份**，跟 OpenList 里 `/aliyun` 用的那份共用会互相踢下线。
2. **安装 / 启动**：拉镜像、起容器（要确认，默认否）。小雅会去它自己的更新服务器下目录、去阿里云盘转存。
   第一次要下几百 MB，过 5–10 分钟再挂。
3. **挂进 OpenList**：挂成 `/xiaoya`。然后回「3 挂载路径」点它，只加要看的几个目录，**别扫整个小雅**（几十万个文件）。
4. **移除小雅**：一次做完（默认否）—— 去掉 `/xiaoya` 的扫描路径、删 OpenList 存储、删容器、删 `/etc/xiaoya`、删镜像。别的盘不动。

卸载媒体栈时，只带走在这里装的那份小雅；机器上原来就有的别的小雅不碰。

## 每天自动做的事

```
北京 03:30  刷新元数据      ← 只有在盘里打开了「自动刷新」才跑（默认关），时刻按盘设
北京 04:10  自动更新脚本    ← 只换脚本，不拉镜像、不重启容器
北京 04:15  刷目录缓存      ← 不刷的话下一步列到的是旧目录，新片一个都扫不进来
北京 04:20  AutoFilm 生成 strm（全局定时，按盘可改）
北京 04:50  对齐：清失效 strm、调续播门槛、补时长、通知 Emby 扫描
每小时      小时对齐：把新内容的库选项/时长/片名/身份拉齐（直链预热默认关）
每小时      链路保活（顺便给体检攒一条 24 小时的曲线）
每分钟      看一眼有没有人点过播放：有就补那一集的时长、盯进度；没人点几乎零开销
每 5 分钟   流量账本记一笔
```

等不到明早就点「`4 生成媒体库`」，它把这三步一次做完。

**手点生成媒体库**分单盘和全部：在某个盘里点的「生成媒体库」只扫这个盘（开头写「单盘 /quark」），主菜单的「4」扫全部网盘（开头逐盘列出）。结尾一行高亮写【单盘 /quark】或【全部网盘】这一轮新增 / 清掉几个。提速三处：AutoFilm 排在约 45 秒后触发（以前要等到两分钟后的整分，没赶上会自动改成两分钟后再排一次）；只报变动给 Emby 时顺手刷那个文件夹，不用等 Emby 自己攒一分多钟；Emby 收下变动后不再把整个库重扫一遍。单盘时，全库那几句「片名 / 集号 / 建库都已对齐」的没事话不上屏，「后台补时长」只数这个盘的。

**这些定时任务和「8 更新」都不打扰正在看的**：有人在播、或者刚播过 10 分钟内，刷目录缓存、每日对齐、刷新元数据、自动更新脚本都推迟到没人播再做（等不到就这一轮不做）；流水里记一行「…让路」。「8 更新」时有人在看会先问一句（默认不更新）；配置没变的容器不重启（重启 MediaWarp 会清空提前取好的直链）；开播门、点了立刻补换了新脚本后，等手上空了自己用新代码重起，不硬停（换链服务更新时照旧重启一次）。

**Emby 自带的 12 小时自动扫库会被关掉**：「8 更新」和凌晨每日对齐时脚本会把它的间隔触发器删掉。原因是每扫一次整个库，刚补上的音视频轨就会被清掉一批（strm 里是网盘路径，Emby 重读时读不出来），开播门下次又得现补。新片不会漏：strm 一有变化脚本自己会通知 Emby。真要留着它，在状态文件里设 `emby_auto_scan_keep: true`，再去 Emby 后台计划任务里加回去。

**同一集第二次点开不再白等**：夸克转码流的盘，换链服务去要播放列表、夸克没给（流水里「网盘回列表 8.0s 没取到（交回 MediaWarp）」），10 分钟内再点这一集就直接交回 MediaWarp，不再去问；开播门那边也不再预取、不再验旧地址。过了 10 分钟或者取到过列表，照常来。

**开播门最多让开播晚 15 秒**：按下播放和紧跟着的第一次拉视频合用这 15 秒，取地址、验直链、等补时长加起来不超过它（以前三段各算各的，最长 35 秒）。只缺音视频轨、时长是有的集，门不补也不等，马上放行，开播两分钟后再在后台补；真没时长的才等，不然退出后进度记不住。这 15 秒是硬上限：门里哪一步卡住（问 Emby、等网盘回列表），到点都先放行，没做完的在后台接着做；`gate.log` 里会记一笔「15 秒到了先放行」，记的秒数是放行用了多久，不含之后的记账。

**开播门排查**：开播门每收到一个请求都记一行到 `/var/log/media-stack/gate.log`（几点、哪一类、花了多久、路径；参数和 token 不记，只有 root 能读）。`media-stack gate-bypass stopping,hold` 可以把其中几类单独放行（gate=按下播放、streamgate=第一次拉视频、peek=点开详情页先取地址、stopping=退出播放插旗子、hold=退出后读详情等进度），`media-stack gate-bypass off` 全部恢复，不带参数看现状和最近的记账。

**每小时对齐给播放让路**：有人正在播或 10 分钟内播过，这一小时的对齐（整理片名、核对集号、同步进度）就跳过，下一小时再做，流水里记一行「小时对齐让路」。

**换了新版本，开播门干净地重起**：「8 更新」或凌晨自动更新换了脚本、此刻没人在播，就把开播门停掉，下次开播用新代码起来。以前等它自己退，换完版本后退出播放进度常常不刷新、要回主页再进才看到。

**尽量不扫整个库**：扫一次整个库，刚补上的音视频轨就会被清掉一批。所以每日对齐（04:50）和每小时检查到 strm 有变化时，只把新增 / 删掉的那几条告诉 Emby，报不了才扫整个库，而且一夜只扫一次（以前 04:50、05:00 连扫两次）。整理过名字的片子，AutoFilm 每晚会按网盘原名再生成一份；现在直接删掉这份，整理好的那份原封不动，不再覆盖。只报「新增」，不报「删除」：Emby 里本地已经没有的空壳条目，由每小时对齐里「清空壳条目」那一步按条目删，不去惊动 Emby 刷新整个文件夹。要挪位置的 strm（凌晨 / 每小时，没人在终端前）也一样：只报新增、最多等 4 分钟，等不到也不扫整个库，留给后面那步再报一次；手点「4 生成媒体库」照旧。1.5.356 起再加一道总闸：凌晨 / 每小时这些没人在终端前的任务，**一律不扫整个库**（只有新建的空媒体库例外）；改了库选项这类必须整库重扫的，记下来，等下次手点「4 生成媒体库」时补扫。每一次「扫整个库」「只报变动」都记在 `/var/log/media-stack/scan.log`（只有 root 能读），写明几点、谁叫的。

**VPS 在哪个时区都行**：上面的时刻都是北京时间，装定时的时候按本机此刻的时区换算（新加坡 = 北京同一时刻，东京晚一小时，美国差十几个小时）。
美国、欧洲那些有夏令时的地方，一年两次偏移会变 —— 每分钟那一轮发现变了，就把这几条定时按北京时间重写一遍，不用等「8 更新」。

**片名纠正**：一部电影单独放一个文件夹时，Emby 拿**文件夹名**去刮削。文件夹名要是「1」「CD1」「4K」「合集」这种，
就会认错（实测「奇异博士/1/Doctor.Strange.2016….mkv」被认成《侠盗一号》）。每小时那一轮会找出这种片，
从**文件名**解析出片名和年份（`Doctor.Strange.2016` → Doctor Strange 2016），让 Emby 按它重新识别 ——
搜回来名字、年份都对得上才改，对不上就不动；不改任何文件。体检里「片名纠正」一行报还剩几部。

**阿里云盘 TV 接口（本机扫码、本机续期）**：阿里盘用「扫码」登录时走 TV 客户端接口。⚠ 它**不解除原画限速**：没开会员的账号，两条接口的原画都只有约 0.7 Mbps（真机实测，一部要 17 Mbps 的片放不动），原画放不动就去「3 直链方式 → 画质」改转码流（跟夸克同一个位置）。
扫码在终端里直接做；令牌续期由本机一个小服务（`media-stack-alitv`，只监听 Docker 内部网络的网关地址，公网连不上）替 OpenList 去做，
从此不经过 api.oplist.org。还剩一个第三方：TV 投屏软件的服务器 api.extscreen.com 看得到这份令牌（夸克 TV 盘本来就在用它）。
防火墙挡住了 Docker 连本机时，续期自动退回 api.oplist.org，盘照样能用。
在「直链方式 → 接口通道」里来回换接口时，换下来的那份令牌留在本机（`/etc/bgpeer/ali-tokens.json`，只有 root 能读），换回去先试它，不用重新扫码或贴令牌；试不通就原样改回、再走扫码。新挂盘、重新登录时清掉。选「扫码 / 贴令牌」和选接口那一问，回车 = 返回（什么都不改），要扫码按 1。终端里画的二维码方不方要看终端字格的高宽比：有的手机终端行距大，码会被拉长、阿里云盘 App 扫不出——等扫码时输 `w` 回车把码横向拉宽（1.25 → 1.5 → 原样轮着换，挑中的记住），屏不够宽会提示先双指缩小字体；网页图片那条链接照留。阿里扫码时先问终端一个字格几像素（xterm 的 CSI 16 t / 14 t 查询，只在本机终端里问答），按真实比例把码横向拉成方的；终端不回就用上次 `w` 挑的那档，都没有就照原码原样画。终端不回字格尺寸的（不少手机 SSH 工具不回）、也没挑过档的：上下画两个码，上面原样、下面拉宽成方的，哪个扫得上用哪个（竖屏放不下就只画原样那个）；输过 `w` 挑中的那档记住，以后只画那一个，它 20 秒没人扫到再换回两个都画。夸克（挂盘、重新登录、本机登录）和 115 的码也一样上下画两种；上面那个永远是网盘给的原码。挂好的 115 盘「网盘扫码登录」跟阿里、夸克一样是「1 扫码登录 / 2 退出登录」：扫完脚本把新令牌写进这个盘、清掉旧 cookie、当场验一遍；不再摊开旧令牌、教人去 OpenList 手填（没挂时的「只拿令牌」那一屏照旧）。等 115 扫码时没人扫就写「等待扫码…」，不再印「状态 None」。要拉宽时才换成重编的小码（解出内容按最低纠错重新编，53 格 → 37 格左右），不然竖屏放不下。各盘「网盘扫码登录」里有「退出登录」（阿里 3、夸克 TV 2、挂好的 115 盘 2）：清掉这个盘在 OpenList 里的登录凭据，盘本身、扫描路径、strm 都不动，重新扫码就回来；换号不用先退，直接扫另一个号。退出时连阿里驱动存的访问令牌（`AccessToken`）一起清，清完当场重新加载一次，连不上了才报已退出；菜单里没凭据的盘写「未登录」。

**夸克清晰度**：OpenList 的夸克 TV 盘在「转码流」方式下只拿夸克给的**第一条**地址，有的片第一条是原片整文件（被限速、拖进度慢），
App 里明明还有 720P / 360P 转码。`media-stack quark-login` 在本机另扫码登一份夸克 TV（另一个设备号，不动 OpenList 那个盘），
`media-stack quark-res <片名>` 把这一部的所有清晰度列出来（只读）。登录凭据只存在 `/etc/bgpeer/quark-tv.json`（仅 root 可读）。
打开夸克 TV 盘设置里的 `9 转码挑档`（**默认关**：实测夸克对转码流一样限速，开播前多问一次夸克还要慢 3~18 秒）后，设成「转码流（有损画质）」的盘在 Emby 里由本机自己挑档：**转码最多降一档**（4K → 1080P、1080P → 720P，
档位按夸克自己的叫法），有同档转码就用同档；再低的一律不要，照旧播原片。`quark-res` 里 ★ 标的就是 Emby 播的那条。

> **这几件事各自花多少流量？** 真正的账全在**补时长**身上，另外两件都可以忽略：
>
> | | 每次拉多少 | 一天大概 |
> |---|---|---|
> | **看片** | **0** —— MediaWarp 302 把播放器直接指到网盘，视频流**根本不经过 VPS** | 0 |
> | 预热直链 | 64 KB/部 × 10 部（库超过 40 部时第三批轮转直接跳过） | ~15 MB |
> | **补时长（heal）** | **约 6.7 MB/条** —— 要让 Emby 的 ffprobe 去网盘拉一段文件头 | **看待探数，见下** |
>
> 所以想省流量，只有一个地方值得动，就是 heal。给预热限速省不下东西
> —— 它现在的量比多数人想的小一个数量级。

## 流量账本（菜单 6）：谁在什么时刻吃了流量

诊断脚本第①栏是**临时采样**，只看得见运行那一刻在跑的东西。而吃流量的几件事全是
间歇性的 —— AutoFilm 一天扫一轮、Emby 扫库在凌晨、heal 一轮几分钟。白天随手跑一次，
大概率什么都看不到，然后误以为「没人在用网」。实测撞过：网卡一天 ↓4.86 GiB，
采样那 30 秒只有 0.05 MB/s。

所以改成**常驻记账**：cron 每 5 分钟记一笔网卡和各容器的增量，按天一个文件，
留最近 14 天。事后能回查任意时刻。

```
流量账本  2026-09-15
  记了 288 格，覆盖约 24 小时 0 分
  物理网卡  ↓4.86 GB  ↑310 MB   ← 只有这一份是真出过网的
  按来源（容器自己的网口，含容器之间的流量，加起来可能比网卡多）
    openlist       ↓  4.10 GB  ↑  3.20 GB   占网卡下行 84%
    emby           ↓  1.80 GB  ↑ 210.0 MB   占网卡下行 37%
    宿主机·非容器  ↓   760 MB  ↑  100 MB    至少这么多
  openlist 从网盘拉了 4.10 GB，占网卡下行 84%
  按小时（网卡下行）
    00 时   ↓  1.20 GB  ############################
    20 时   ↓   980 MB  #####################
```

**「按小时」那一栏后面会点名大头是谁**，这是分辨「Emby 在吃」还是「代理在吃」
最快的一眼：

```
  按小时（网卡下行 · 后面是这一小时的大头是谁）
    02 时   ↓  1.38 GB  ↑   5.0 MB  ############ openlist 1.30 GB  宿主机 81.9 MB
    04 时   ↓  97.0 MB  ↑   507 KB               openlist 90.0 MB  宿主机 7.0 MB
    13 时   ↓ 145.0 MB  ↑  65.0 MB  #            openlist 12.0 MB  emby 8.0 MB  宿主机 125.0 MB
```

02 时和 04 时是 openlist（Emby 这边在探测），13 时是宿主机（你在用代理）——
**同样是一百多 MB，来源完全不同**。没有这一栏的话，「每小时稳定一百多 MB、一直在跑」
只能看见、答不出是谁。

**「按任务」那一栏回答的正是「凌晨那次自动对齐扣了多少」**：五个定时任务
（目录缓存 / 每日对齐 / 直链预热 / 补时长 heal / 链路保活）跑的时候会记下起止时刻，
报表把落在那个窗口里的格子加起来：

```
  按任务（定时任务各跑在什么时候，那段时间网卡跑了多少）
    06:10  目录缓存     跑了 1 分    窗口内网卡 ↓0 B
    06:45  每日对齐     跑了 22 分   窗口内网卡 ↓350.0 MB
    07:08  补时长heal   跑了 17 分   窗口内网卡 ↓58.3 MB   （自测 1980 MB/天累计）
```

「窗口内网卡」是**上限**，不是精确值 —— 同一时段你要是正好在用代理，那份也算进去了。
heal 那行括号里的数是它自己拿网卡差实测的，比窗口值准。任务**跑挂了也会记**，
那一次同样烧了流量，恰恰最该被看见。

**「宿主机·非容器」那一行别忽略**：代理节点（sing-box / xray）是 systemd 服务、
**不在任何容器里**，所以它的流量永远不会出现在上面几行。看到「容器全是几百 KB、
网卡却跑了 43 MB」，差额就在这一行里 —— 那多半就是你在用代理。
这一格是「网卡 − 各容器」算出来的，容器之间的流量会把它压小，所以只说「至少」。
它的**上行**常常减不出正数（容器发给本机 nginx 的那部分不经网卡，却记在容器名下），这时写「算不出」，不是「只进不出」。
它的**下行**里常有一大块是**商家网段的 ARP 广播**（同网段别的机器在问 IP，真机抓 60 秒：进来 2.95 MB 里占 1.74 MB）——
夜里没人用也每小时一百多 MB，不是哪个程序在下载，本机也拦不掉（到了网卡就已经计数了）。

**怎么读**：`openlist` 是整条链路上唯一真正出境拉数据的一环，它占网卡下行的比例
就是「流量到底是 Emby 吃的、还是代理节点吃的」的答案 —— 占比高是 Emby 这边
（探测 / 补时长 / 扫库），占比低说明剩下的是节点转发的。

容器那几行是**各自网口**的量，包含容器之间的流量（emby 找 nginx 要文件头也走
veth），所以加起来可能比网卡还多，两者不是分摊关系。**只有物理网卡那一份是真出过网的。**

账本里的小时、日子、任务时刻**一律北京时间**，不管 VPS 摆在哪个时区（东京那台以前差一小时）。
账本在 `/var/log/media-stack/traffic-YYYY-MM-DD.tsv`（0600，目录 0700，按北京日子起名）。
命令行看：`media-stack traffic [日期]`。

常用命令（全部见 `media-stack help`）：`media-stack traffic [日期]` 流量账本 / `media-stack play-report [小时]` 开播报告 /
`media-stack heal-log [行数]` 补时长流水 / `media-stack heal <片名>` 手动补一部 / `media-stack play-check` 每个盘照播放器路子过一遍 /
`media-stack quark-res <片名>` 夸克这一部的所有清晰度 / `media-stack meta-refresh <挂载点>` 这个盘的自动刷新元数据（自动关着不跑）。

## 点播放之后：先补这一集、别的让路、盯住进度

* **只补你点开的那一集**：点播放之后的 30 分钟里只补这一集（已经有时长就不补），不顺带补别的片；积压的等这 30 分钟过了、没人再点播放才补。
* **别的活一律让路**：截封面（每小时那档和生成媒体库后截新加的）、直链预热也一样，这 30 分钟里不碰网盘，干到一半有人点播放就停下；一睡着，没干完的马上接着干（预热最多一分钟内补跑）。「最后一次播放后 30 分钟内」按开播门和每分钟那一轮记下的播放时刻算，跑「8 更新」重启了那个小服务也不会误以为没人在用；问不到 Emby 有没有人在播时也先让路（以前当成没人，真机一次更新后边播边补了 45 部、约 298 MB）。
* **日志里记着每个请求等了多久**：媒体站那份 nginx 日志（`/var/log/nginx/media-stack.access.log`）每行末尾多了 `rt=` / `urt=`（这个请求一共花了几秒 / 后面 Emby、MediaWarp、门回话花了几秒），前面跟 nginx 默认格式一样。退出后进度没刷新时，看得出是播放器没来读，还是读了、卡在 Emby 那边。
* **第一次拉视频时也守着**：从「继续观看」直接点播放，Hills 只问一次播放信息，跟点开详情页一模一样，门分不出来；所以播放器**第一次拉视频**时门再问一声 —— 这一部还没时长就先补好再给视频（大约等几秒），有时长的马上放行；同一集查过一次，十分钟内再拉不再问。只翻详情页不拉视频，不会误探。门挂了照样放行。改了 nginx 配置，要跑一次「8 更新」。
* **「下一集」也算开播**：播放器里点下一集 / 上一集（刚「停止播放」5 秒内问别的一集），门照样先预取、先补时长。
* **打开详情页就先取地址**：打开一部剧 / 一集 / 一部电影的详情页，后台马上把待会儿多半要点的那一集的地址取好（剧取看了一半的那集，没有就取下一集；只换地址、不拉视频），按播放时直接命中缓存 —— 网盘接口慢的时候（真机一次给地址 24 秒），打开详情到按播放那十几二十秒正好盖住。只取 302 直链的盘（走本机代理的 WebDAV 这类不取）；同一集半小时一次，同一时刻只取一个；在播的时候不取。改了 nginx 配置，要跑一次「8 更新」。
* **下一集先取好地址**：开始看一集 30 秒后，后台把同一部剧下一集的地址先取好（只换地址、不拉视频；电影不取；同一集半小时只取一次），点下一集直接命中缓存。
* **盯进度**：还有人在播就不睡（半小时从播完那一刻算起）；醒着时每 3 秒记一次正在播的那一集放到哪儿，退出后 Emby 记的续播点比它早 15 秒以上就写回准的那个。
* **退出后页面排在进度后面**：在播的整段时间里常驻服务插着一面「正在播」旗子（写着哪几台设备）。旗子在时详情、剧集页、继续观看、下一集都先到门那里问一声 —— 是正在播的那台设备来读，就先等「停止播放」到、等 Emby 记完再放（1.5 秒都没来、还在播就是播放中自己在取东西，放行）；别的设备来读不等。
  播放器喊「停止播放」那一刻起，任何一集的详情都先等 Emby 把这一场记完（最多 3 秒），不再读到旧进度。这一条改了 nginx 配置，装好后要跑一次「8 更新」。

## 换链服务：要地址卡住时替播放器扛着

换链服务每台都装，不管有没有盘用转码流（`media-stack hls-direct off` 关掉直出才回到只按转码流判）。

* **MediaWarp 没给地址**（网盘接口一时卡住）：隔几秒再问，最多问 4 次、替播放器扛 50 秒，不再把 404 直接交给播放器。
* **并发补问**：一下问出去 10 秒没回，不掐它、再补问一下，谁先回用谁（平常同时最多 2 下）—— 跨境接口第一下卡住时不再干等 35 秒、把播放器等到自己退出。
* **上次的地址还活着就直接用**：看地址自己写的过期时刻（夸克 TV 实测转码流约 3 小时、原画约 4 小时），够放完这一集就用，过期的不去拉；转码流半小时内的直接先用，原画 / 115 / WebDAV 整文件直链先验 1 个字节再用；MediaWarp 5 秒没回话就先验上次那条。
* **拉播放列表最多 8 秒**：网盘节点一点一点往外挤的不再干等，拉不动就换上次那条，再不行交回给播放器自己拉。
* **阿里转码流**：按它自己的过期时刻缓存；要新地址 8 秒没回先用没过期的旧地址；手里什么都没有就多等一会儿（最多 25 秒），不轻易退回被限速的原画；拿到的档位比设定的低（阿里第一次点开往往只转好了 SD），过两分钟再问一次，有高的就换上。
* **115**：直链按 `t=` 过期时刻缓存，要新的 8 秒没回先用旧的（先用播放器的身份验 1 个字节），手里没有最多等 20 秒；不同播放器各要各的。

## 盘和盘互不拖累

* **认盘**：一律按「这一集在哪个挂载点（最长前缀）+ 那个挂载点是什么驱动、怎么设的」，不看它在不在「剩余网盘」里 —— 剩余网盘一次挂好几个盘、挂载点是两层（`/网盘/天翼`）时，每一集照样走它自己那个盘的路。换链服务一集先认在哪种盘上（阿里转码 / 115 / 其余），之后只走那个盘自己的路；115 盘的挂载点表放后台刷新，开播不等它。
* **改设置只动这个盘**：登录、退出、换接口、直链方式经 OpenList 接口只重新加载这个盘，不停 OpenList、不重启 MediaWarp、不把所有盘后台预热一遍（接口不通才退回老办法）。
* **一集的直链死了只换这一集**：开播前验出缓存的直链死了，这一集改由换链服务现换，不重启 MediaWarp；阿里原画（直链 15 分钟）由换链服务现换，不再把所有盘的直链缓存从 2 小时压到 9 分钟。
* **限流按盘算**：补时长撞限流，撞满的那个盘这一轮停下、下一批砍半，别的盘照常补、照常并发；预热各盘轮流热，一个盘接线超时两次这一轮就不再热它。

## 自检：`play-check` 和 `play-report`

* `media-stack play-check`：媒体库里每个盘挑一部，照播放器的路子过一遍（要地址几秒、原画还是转码、阿里拿到哪一档、相对分片指不指得回去、VPS 拉几秒的速度够不够），每个盘一行；不碰进度、不触发补时长，只在你亲手敲的时候跑。
* `media-stack play-report`（或 `play-report 48`）：最近 24 / 48 小时你自己点的播放，每个盘开播几次、要地址几秒（中位 / 最长 / 超过 10 秒几次）、有没有重问 / 用旧地址兜底 / 分片 404、开播门等了多久、最慢的 5 次；夜里的定时任务（生成媒体库、补时长、截封面、预热）另列一段、附上那段时间的下行，不算进开播。
  开播次数按门和换链服务里同一集 2 分钟内不重样的算（在播放器里点下一集这类门没记的也算上）；「阿里没给地址」只记在阿里转码盘上的片子。
* 数据是换链服务和开播门经手真实开播时顺手记的一行（几百字节，不记地址），不多发任何请求，root-only，跟流量账本一起留 14 天；play-check / play-speed 自己打的请求不记。时刻都是北京时间。

## 刷新元数据：为什么只补缺的

新出的集 TMDb 往往还没写中文简介，Emby 只在入库那一刻刮一次，而初次导入后的自动联网刷新是脚本关掉的（开着会把 strm 的音视频轨刷没），所以 TMDb 后来补上了也拿不回来 —— 这就是每个盘那一项「刷新元数据」。

* 挑的是**缺简介或缺图**的电影、剧集、整部剧，齐全的不碰。缺简介的连图一起补（只补空着的字段，片名、季集编号不动）；只缺图的只刮图，不碰别的字段。
* 刷元数据只问 TMDb 几 KB；但缺简介的那几部 Emby 会顺手清掉音视频轨，几分钟后自动补回（每部从网盘拉几 MB）—— 所以不全库刷。
* 自动刷新默认关；开了每天按设的时刻（默认北京时间 03:30）跑一轮，只看入库 60 天内的：两周内的每晚试一次、之后一周一次，一轮最多 120 部。TMDb 上也没有的照样空着，等那边有人补上才刷得到。

## 容器网络的 MTU

跟着 VPS 出口网卡走：网卡比 1500 小（有的商家是 1450 / 1400）时，「8 更新」会把容器网络按网卡的值重建一次；1500 的机器什么都不动。

## 补时长（heal）为什么会烧流量，以及怎么治

> ⭐ **最有效的一条：只补你点开过的。** 没有设置项，就这一种行为。
>
> 补时长的唯一用途是**进度条和续播记忆**——而没点开过的条目，补出来的进度条给谁用？
> 库里两千多部，点开过的几十部：这一条把每天的流量从 GB 压到 MB。
>
> **它不会让你少看一部片**：没探到的条目照样能播——Emby 在你点播放那一刻会现场探一次，
> 代价只是开播前多等几秒。而**那一次点开本身**就把它放进了播放记录，下一轮就补上——
> 需要进度条的那一刻，进度条就在。
>
> 判据是**播放记录**（继续观看 + 已看完），按**每个账号**收：电视一个号、手机一个号是
> 常态，只认第一个号会漏掉一半。筛选只读 Emby 自己的库，**一个字节的网盘流量都不花**。
>
> 日上限 `HEAL_DAY_MB`(2048) 留作**兜底闸门**，不做成菜单项——日常已经压到几十 MB，
> 它是给意外情况留的保险；多一个旋钮就多一份「设错了怎么办」。
>
> 体检里的「条目时长」报的是**全库**待补数，并会说明其中你点开过的有几个——
> 免得看到「还差 2583 个」以为它卡住了，其实剩下的是**故意不补**的。

> **它每小时都在跑，不是一天一次。** `do_warm`（每小时）会调 `align_library()`，
> 而那个函数默认 `heal=True` —— 所以 heal 一天最多被触发 24 轮，靠 `HEAL_DAY_MB`
> 这个**日**上限刹车，而不是靠"一天只跑一次"。
>
> **额度是轮内检查的**：每探 10 个就量一次实际花销，超了当场收工 —— 排队还没轮到的
> 一个都不发。以前只在开轮前查一次、跑完才结账，一轮就能冲过头（现场 00~02 时花了
> 约 2.8 GB，而上限是 2048 MB，超了四成）。
>
> 量的是 **openlist 容器自己的收字节**，不是物理网卡。网卡是全机的，会把你同一时段
> 用代理的流量也算进来 —— 拿它当刹车，你一看片 heal 就被判超额停工，积压永远补不完。
> 拿不到 openlist（没装 docker / 容器没起）才退回网卡。
>
> 账本里它现在是**独立一行**。以前不是：因为嵌在每小时那条任务里跑，账全记到
> 「直链预热」头上 —— 现场一度看到「直链预热跑了 22 分、窗口 973 MB」，
> 而 README 写的是「预热 15 MB/天」，两边差两个数量级，人就被带偏了。
> 那条任务现在也改叫 **「小时对齐」**，因为预热只占它一小角。

`.strm` 媒体库里 Emby 探不到时长，进度条和续播就整个失效（它按时长的百分比判断续播点，
分母为 0 直接判「已看完」）。所以 `heal` 每小时挑一批没探到的条目，**临时把 strm 切成 URL 形式
让 Emby 去网盘拉一段文件头**探测，探完切回来。每探一个约 6.7 MB（从上游算约 18 MB）。

**原来缺了「放弃」这一步。** 判据是「缺时长 **或** 缺音视频轨」，而轮转游标只保证「不把名额占死」，
不保证「别再探」。一台现场机器实测：

```
总条目 2727   缺时长 7   缺音视频轨 2697（98%）
28 天探了 93868 次，单个条目最多 135 次、跨 7 天，一次都没成功
```

那 2697 个是网盘上的残缺文件 / Emby 不认的格式 / 上游挡探测 —— **怎么探都探不出来**，
于是每小时循环探全库，**30 GB/天，零收益**。

现在记一个**持久的失败计数**：连续失败 `HEAL_GIVEUP`(3) 次就不再提供给 heal，
`HEAL_GIVEUP_DAYS`(30) 天后自动再给一次机会（万一源头修好了）。成功一次就把记录抹掉。
限流（429）和「本地没这个文件」**不算这个条目的失败** —— 那是上游和环境的问题，
拿它们累加会把好条目误判成放弃。

按现场的数据：原来每天 24 轮 × 2727 = 65448 次探测，修后建立记忆的 3 轮之后
每天只剩 24 × 30 = 720 次，**降到 1%**。

**探完了和没探成，是两回事。** 判定失败分两种，攒账方式也不一样：

| 情形 | 说明 | 记几次 |
|---|---|---|
| 探测请求本身没跑成（超时、断开） | 线路抖了一下，重试往往就成 | 1 次，攒够 `HEAL_GIVEUP` 才放弃 |
| **探测跑完了，Emby 明说这个源没有音视频轨** | **确定的答案** | **一次就记满，直接放弃** |

第二种再探两次只是把同一个答案买三遍，而**一遍的价钱是「全库 × 每个几 MB」**。
现场那台 2697 条的库实测：一遍 18 GB，攒三次就是 **53 GB**；改成一次判定之后
降到 **18 GB**，也就是把全库过一遍就收工。判错的代价很小 —— 体检那边照旧如实
报它，`HEAL_GIVEUP_DAYS` 天后自动再给一次机会。

**再加一道按字节算的硬闸。** 上面那些（放弃名单、轮转、时间预算）都是「尽量少探」，
但没有一条给得出**承诺** —— 而机器是按月计费的，「尽量」不够用，超了就是超了。

所以 `HEAL_DAY_MB`（默认 2048）是每天的流量上限：**用满就停，明天零点自动清零接着来**。
取批的时候也按剩余额度夹一刀 —— 不夹的话最后一轮一次 300 个 × 约 7 MB = 2 GB，
等于把上限当摆设。总量不变，只是摊开到几天。

记账用的是**本机物理网卡的接收字节差**（`/proc/net/dev`，排除 `lo`/`docker*`/`br-*`/`veth*`
免得把容器间的往返数两遍）。**播放走 302 直链、根本不经过 VPS**，所以这段时间的接收量
基本就是 heal 自己拉的。读不到计数才退回按次数估。每轮跑完会打一行：

```
  这轮花了约 180 MB（实测）；今天累计 1420 MB / 上限 2048 MB，还剩 628 MB
  跟 2026-09-13 比：待探 -2397（现在 300 个），放弃名单 +2400（现在 2400 个）
```

第二行是**每天记一次的增减**。为什么值得单独有：待探数是个**余额**，它不动不代表没干活
—— 可能今天探好了 20 个、同时又新扫进来 20 个。只盯余额会以为 heal 根本没在工作。

**放弃之后再试的间隔越来越长。** 固定 30 天是不够的 —— 一个**永远探不出来**的库
每个月都会被完整重探一遍（2697 条 × 6.7 MB = **18 GB/月，而且永远这样下去**）。
那不是「放弃」，只是把「一直探」从每小时改成了每月。

所以按放弃次数翻倍：`30 → 60 → 120 → 240 → 360(封顶)`。一个永远探不出来的条目，
一年里只会被碰 4 次左右而不是 12 次 —— 同一个库从 **229 GB/年降到 71 GB/年**。
源头真修好了的话，**一次探成功就把记录抹掉、计数归零**，不会被退避拖住。

确实修好了源头（换了网盘、改了格式、上游不再挡）想让它们重新排队：`media-stack.py heal-reset`。
体检那边报的仍是**真实待探数**，不会被这个名单藏起来 —— 那是给人看的诊断。

## 常见问题

**刚往网盘里加了片子，Emby 里没有？** 先想到目录缓存：OpenList 默认缓存 30 分钟
（在「`7 设置 → 6`」里改，最短一档 1 分钟＝基本实时），缓存没过期之前
**OpenList 自己都看不见新文件**。点「`4 生成媒体库`」会先把缓存清掉再扫。

缓存长短是个取舍，两头都有实实在在的代价：**调短**新片马上看得见，代价是翻目录更常撞上
网盘对列目录接口的限流（表现为转圈几十秒）；**调长**翻目录顺滑，代价是新片要等缓存过期。
每天 05:10 那次会自动刷，所以调长**不影响**「每天自动把新片扫进来」。

**OpenList 挂载页面时断时续、隔一阵就连不上？** 跑「`5 链路体检`」看**容器稳定性**那一行：
它报的是累计重启次数和有没有被系统 OOM 杀过 —— 内存不够被杀是这种间歇故障的头号原因，
而事后去看进程又好好跑着，光看「容器 ✔ 在跑」永远发现不了。同一屏的**保活历史**能分出
「一次已经过去的掉线」和「长期抽风」：失败扎堆 = 那次已经好了，失败散布 = 真在抽风。

页面报 `context canceled` 不等于网盘拒绝了你 —— 那是**浏览器等不下去先断开**，
OpenList 顺手把上游那条也取消掉，说明的是「慢」而不是「被拒」。

**一屏片子全都「没热上（HTTP 404）」？** 这不是网盘慢，是 MediaWarp 换直链被拒了。
它只在**启动那一刻**登录一次 OpenList，OpenList 一重启旧令牌就作废 ——
敲 `docker restart mediawarp` 就好。表现在播放器上是点开一直转圈，
而已经缓存过直链的片子照样能放，所以看着像「有的能放有的不能放」。

## 诊断脚本（`tools/`，都是只读的）

| 脚本 | 干什么 |

| `why-stall.sh <片名> [秒数]` | **「能播，但过几秒卡一下」专用**：不用你去点播放，脚本自己**当一回播放器**把这部片拉一遍 —— 一段一段地要、缓冲满了就歇手、播掉了再要，每秒记一次缓冲水位，最后画成一条时间轴（`█` 充足 / `▃` 快见底 / `✖` 见底＝这一秒在卡）。**这是 `cant-play.sh` 测不到的那一层**：它最多连着**全速**拉 4 秒，而"卡一下"根本不是拉不到数据，是这一秒该来的那段没按时到；而且很多源是按连接算令牌的，**你歇手这件事本身**就是被降速/被断流的触发点，全速拉永远撞不上。时间轴的形状直接分出三种在客户端上一模一样的病：周期性断流（源在限速，改配置改不掉）、一路衰减、纯粹带宽不够。同一个文件还会走**两条路各拉一遍**——网盘 CDN 直链 vs 经过你 VPS 的本机代理——**不用真去改配置**就能先量出"这个盘该不该开本机代理"。末尾再翻一遍 MediaWarp 和 nginx 日志，看这部片**真被人播**的时候到底发生了什么（401 风暴＝这个盘设成了转码流）。按播放码率拉，一条路 45 秒 ≈ 码率 × 45 秒的流量，跑之前屏上先报数。**播着的时候跑它，还能答另一种病：「网速跑到 30 M/s，画面半天不出来」**——取流那几节会一路绿灯，因为取流真的没问题；末节会去问 Emby 此刻的 `PlayMethod`，是转码就把**转码帧率 ÷ 源帧率**算出来（转出 3 fps、源片 24 fps ＝ 0.12 倍实时，客户端每等 8 秒才拿到 1 秒画面，进度条自然一直挂在 0:00），再看 ffmpeg 吃没吃满 CPU 分出「机器就这个水平」和「ffmpeg 在等输入」。**直链修得越好、流量数字越漂亮，这种病越像网络问题** |
| `ol-file.sh <网盘路径>` | 「OpenList 网页里点开一直转圈」专用：列目录 / 取播放地址 / 拉 1 MiB 三步分开计时，再附上 OpenList 自己的报错原文（令牌已打码） |

| `why-slow.sh <片名>` | 从 Emby 到网盘的整条链路挨个量一遍 |
| `ali-403.sh <片名>` | 换五种方式拉同一条直链，几条路速度齐平就说明是限速而不是线路 |
| `compare-speed.sh` | 把 MediaWarp 302 和 OpenList 转码流并排比 |
| `ali-token.sh` | 查阿里的类型和令牌配不配对 |

| `dav-upstream.sh [挂载点]` | **「这个 WebDAV 盘的流量到底躲不躲得掉」专用**：`dav-check.sh` 问的是 OpenList 这一头，这个脚本去问**上游**。WebDAV 盘现在一律走本机代理、视频字节全程过你的 VPS，理由是「WebDAV 发不出公网直链」—— 但那是从协议推出来的，不是量出来的，而协议留了个口子：WebDAV 的 GET 允许回 302，有些做影视库的上游正是先在自己那儿鉴权、再把你丢给一个带签名的 CDN 地址。**上游回 302 就有救**（这台机器只要替播放器挨那一下 302，之后几个 G 一个字节都不过 VPS，和转码流的分片重定向是同一个套路）；**上游直接给字节就没救**（凭据在 `Authorization` 头里，播放器发不出这个头，换什么配置都一样）。两种在客户端上长得一模一样，差别只在你的流量账单。屏上只出现主机名 —— 账号密码和 302 目标里的签名一个字符都不打 |

⚠️ **拉这些脚本会拿到旧版**，而且屏上看不出来 —— 每个脚本第一行都会打印自己的
`版本 xxx`，对不上就是拿到旧的了（不是「改了没用」）。

`raw.githubusercontent.com` 有 CDN 缓存，**加 `?_t=$(date +%s)` 挡不住** —— 实测：
带着时间戳连拉两次，拿到的都还是几分钟前那一版。可靠的办法是**指定提交号**：

```bash
SHA=$(curl -fsSL https://api.github.com/repos/bgpeer/nodekit/commits/main | \
      sed -nE 's/.*"sha": "([0-9a-f]{40})".*/\1/p' | head -1)
curl -fsSL "https://raw.githubusercontent.com/bgpeer/nodekit/$SHA/tools/xxx.sh" -o /tmp/xxx.sh
```

提交号是内容的一部分，那条 URL 永远只对应那一份文件，不存在缓存问题。

## 六条硬限制

⚠️ **夸克必须用 `QuarkTV` 驱动**才支持 302；普通 `Quark` 驱动因限速只能本机中转，
那样流量仍然全走你的 VPS，等于没做直链。

⚠️ **不能转码**：文件在网盘上，Emby 拿不到本地文件，只能原盘直出，
客户端不支持的编码就播不了（换 Infuse / VidHub 比换服务器管用）。

⚠️ **代理型存储（WebDAV 源、本地目录、加密层）要填「网站 URL」才能在 Emby 里播**。
这类驱动在网盘侧**没有 CDN 直链**，OpenList 只能把自己的 `/d/` 地址当直链回给你；而那个
地址的主机名是**谁来问就按谁用的主机名拼** —— MediaWarp 在容器里用 `http://openlist:5244`
去问，拿回来的就是 `openlist:5244`，302 给手机电视就是 `Name or service not known`，
客户端上只有一句 `load fail`。整条链每一步都「成功」，只有最后那个地址是废的。

OpenList v4 **没有「网站 URL」这个设置**（v4.2.6 的设置里带 url 的只剩 `site_title` 和
`qbittorrent_url`），改不了它。所以脚本从另一头改：让 **MediaWarp 用对外地址去问 OpenList**
（`alist_strm.list[].addr`），OpenList 拼出来的自然就是对外地址 —— nginx 那边 `Host` 和
`X-Forwarded-Proto` 都是原样透传的。「`8 更新`」会自动改好，**探不通就退回内网地址**
（不然域名解析不了会让所有盘都换不到直链，比一个盘播不了严重得多）。
「`5 链路体检`」里有 `MediaWarp→OpenList` 这一项。

这类盘的视频**会经过你的 VPS**，那是驱动本身决定的，改不掉。

⚠️ **音轨也算在「不能转码」里**，而且它是最容易被误判成「服务器坏了」的一条。
原盘压制常带 **TrueHD / DTS-HD** 音轨，手机、浏览器、多数第三方客户端都解不了。
解不了时 Emby 会要求**只转音轨**（画面直出）—— 而这套东西连这个都做不到，
服务器手里根本没有那个文件。结果是客户端拿不到可播的源，**瞬间 `load fail`**，
而且它连 `/stream` 都不会去请求，**MediaWarp 日志里一条记录都没有** ——
看日志会误以为「请求没到 MediaWarp」，于是一路往服务器那头查。

一句话自查：**去 OpenList 挂载页面播一次**。
**有画面、没声音 = 就是音轨解不了**（挂载页面用的是浏览器解码器，浏览器只认
AAC/MP3/Opus/FLAC）。出路只有换播放器（Infuse / VidHub / Kodi / 电视盒子）
或换片源（AAC / AC3 音轨的压制版），服务器这头做什么都没用。

⚠️ **蓝光原盘目录（BDMV）不是一个文件**，strm 里只装得下一条指向**单个文件**的地址。
Emby 一看见 `BDMV` 目录就把整个文件夹认成一个「蓝光原盘」条目（容器写 `Bluray`），
播放要按索引在几十个 `.m2ts` 之间跳 —— 那需要本地目录。表现是**大小 `0B`、码率 `0bps`、
点播放 `load fail`**，跟网盘是哪一家、线路好不好、直链方式怎么选都无关。

**默认：原盘不进库。**（`3 挂载路径 → 选盘 → 5 不扫的目录 → 3 原盘怎么办`）
把 `BDMV`/`CERTIFICATE` 那两棵**本地 strm 树**删掉，网盘上的原盘一个字节都不动，
开关改回去再扫一次就全回来。这样默认，是因为：原盘进库必定是坏条目；而它在库里
和能播的那份**同名同海报**，点中坏的那个概率是一半。

改成 `2 压成单个 strm` 的话，取 `BDMV/STREAM` 里最大的那个片段（＝正片），在原盘目录里
生成一个同名 strm，之后 Emby 就当成一部普通电影来刮削和播放，302 照常。
⚠️ 那多半是 **20 GB / 24 Mbps / TrueHD 7.1** 的正片——跨境网盘线路未必拉得动，
音轨多数客户端也解不了（而文件在网盘上，Emby 没法转码）。「`4 生成媒体库`」和每天的
对齐都会按当前这个开关办。
片段清单**问网盘要**，不看本地扫出了几个 strm —— `.m2ts` 不在 AutoFilm 的默认扩展名
表里，一套几十个片段的原盘本地常常一个 strm 都没落下，那种恰恰是最该压的。
问不到片段大小（列目录超时）时**一个文件都不动**，下一轮再试 —— 随便挑一个的话，
点开是厂标或菜单动画，那比播不了更难受。

⚠️ **上游网盘会按 `User-Agent` 挡人**，而 Emby 的探测用的是 ffmpeg 的 UA。
实测同一个文件、同一段时间、同一条直链：

| 谁在请求 | User-Agent | 结果 |
|---|---|---|
| Emby 的 ffprobe | `Lavf/59.27.100` | `429` |
| 体检脚本（以前不带 UA） | `Python-urllib/3.12` | `403` |
| 手机 / 电脑浏览器 | `…Chrome/…` | `429`、`429`、`429`，然后 `206` / `200` |

只有 UA 不同。浏览器 UA 撞几次限流之后拿得到数据，非浏览器 UA 一次都没成过。

后果是**条目里一条音视频轨都没有**（`媒体流 0 条`）。

⚠️ **「媒体流 0 条」不等于播不了** —— 这里曾经写成「必定 `load fail`」，实测被推翻了：
一个 0 轨道的条目（1.73 GB / 119 分）照样连续播了 40 秒，同一时刻 nginx 日志里有播放器
的 `206`。真相是 **Emby 在你点播放那一刻会现场探一次**：

| 那一刻源的状态 | 结果 |
|---|---|
| 给得出数据 | 能播，只是**开播前多等几秒** |
| 正在限流 / 挡 UA / 超时 | `load fail` |

也就是说 **0 轨道的条目每次播放都在押一次运气**，而且每次都要额外向网盘拉一段。
上游按 UA 挡人的那几天这个运气一次都押不中，于是看着像「必定播不了」。

补探测仍然值得做：补上之后 Emby 直接拿库里那份，**开播更快、也不用每次押运气**。

诊断脚本自己戴着浏览器 UA，所以它也一路报好 —— 这是这条最难查的地方。

那些 `429` / `403` **不是 nginx 发的，也不是 OpenList 发的**。OpenList 是透明代理
（`server/common/proxy.go`：`ProcessHeader` 把客户端的每个头连同 UA 原样带去上游，
再把上游的状态码原样写回），所以看到的就是**上游服务器的脸色**。

脚本的处理是一个**按盘的开关，默认全关**：
`3 挂载路径` → 选那个盘 → `2 直链方式` → **探测 UA**。开了之后，本机 nginx 会把
**这个盘路径下**的探测类 UA（`Lavf/…`、`ffmpeg`、`ffprobe`、`Python-urllib`、
`Go-http-client`、空 UA）换成浏览器 UA 再送进 OpenList。`curl` / `wget` **故意不改写** ——
留一条能看见上游真实脸色的路，不然诊断出来的全是改写后的结果。

⚠️ **一定要一个盘一个盘地开**。曾经把它做成全局的，结果所有盘一起换脸：探测确实过了
上游的 UA 那一关，可紧接着一股脑打过去，上游转而**按频率限整个源**（体检那行从 `403`
变成 `429`），连挂载页面都连不上了 —— 为了修一个盘，把另外三个好好的盘一起拖下水。
所以开完去挂载页面播一部片子确认一下，不对劲就回同一个地方关掉（关掉后生成的 nginx
配置和没有这个功能时**逐字节相同**）。

只有**代理型**的盘会显示这个开关。脚本自己发的请求另外统一带完整浏览器 UA，
并且**碰到 `429` 会退避重试**（上游即便认了 UA 也还按频率限）。

**够不着的一种**：夸克 / 阿里这类**有 CDN 直链**的盘，Emby 是跟着 302 直接去网盘 CDN 的，
那条请求不经过本机 nginx，UA 改写碰不到它。真被 CDN 按 UA 挡住时，只能把这个盘的
「回源方式」改成本机代理（`3 挂载路径` → 选那个盘 → `2 直链方式`），代价是视频过本机带宽。

`tools/cant-play.sh` 的 **⑧** 就是测这个的：同一条直链换四个 UA 各问一遍，
再分「绕过 nginx」和「经过 nginx」两路对照，一屏就能分出是**按 UA 挡**、**按频率挡**，
还是 UA 根本不是问题。
